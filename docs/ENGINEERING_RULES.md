# ENGINEERING_RULES.md — инварианты, стоп-гейты и guard-условия

Проект развивался 50+ итерациями с AI-агентом для кода. Каждая итерация
начиналась с постановки-промпта, а между ними действовал постоянный файл
правил (системный промпт агента, `CLAUDE.md` в рабочем репозитории). Этот
документ — его обезличенная выжимка: правила, которые не дают системе
деградировать, когда код меняют часто и быстро.

Принцип: **сначала разведка данных, потом код**. Любая правка алгоритма
начинается с запроса к живому каталогу («сколько строк реально затронет
изменение, есть ли такие значения в данных вообще»), а её результат
записывается рядом с кодом. Почти каждый guard ниже появился из конкретного
промаха, найденного такой разведкой.

---

## 1. Инварианты (проверяются в каждой приёмке)

| Инвариант | Почему |
|---|---|
| Число строк каталога после сборки фиксируется в правилах и сверяется после каждой итерации; любое изменение объяснено построчно («+16 лент», «+80 набивок») | молчаливая потеря или задвоение строк при правке парсера — самый дорогой класс ошибок |
| Контракт таблицы `catalog` — ровно 26 колонок в фиксированном порядке (`core.COLS_DB`), `sku` уникален | на таблицу завязаны GUI, CLI и внешняя интеграция; схема меняется только вместе с DB_SCHEMA.md |
| Проверка данных прайса: `check.py` — 48/0 при `KNOWN_PRICE_ANOMALIES = 5` | 5 аномалий — ошибки самого прайса поставщика. Их фиксируют, но «чинить» в коде запрещено: так маскировалась бы реальная проблема источника |
| Регрессионная четвёрка команд с точными ожидаемыми числами (число позиций, сумма КП до копейки, «4 строки», «32 строки»…) | короткий smoke-тест сквозного пути; при осознанном изменении числа рядом пишется причина («было 67, стало 32: 35 колец проходили фильтр давления без давления») |
| Новое правило в нейтральном положении (все настройки `null`) даёт результат **побайтово** как в эталонной итерации | главный регрессионный инвариант модуля бизнес-правил: настройку можно добавить, не меняя поведения по умолчанию |
| `XFAIL` обязан падать: если он вдруг проходит (`XPASS`), это `FAIL` | известное ограничение ядра описано тестом; если ядро исправили, пометку снимают явно, а не случайно |
| Перф-бюджет в тестах: `diagnose_analogs` < 1 с, `find_cross_analogs` < 0.5 с, весь набор < 90 с | после оптимизации (кэш разбора размеров) регрессия скорости ловится тестом, а не жалобой пользователя |

Итог по тестам рабочей версии: 178 проверок (107 сквозных на живом каталоге,
19 + 3 XFAIL на модуль сопоставления со складской номенклатурой, 4 на слой
интеграции, 48 проверок данных прайса).

## 2. Стоп-гейты (что агенту запрещено без явной задачи)

- **Границы модулей.** Парсеры, сборка каталога, проверка данных и ядро
  справочников (`parsers.py`, `catalog.py`, `check.py`, `core.py`) меняются
  только явной задачей. Если правка выходит за границу, это фиксируется
  как «отклонение от границ» с обоснованием. Пример: векторный дубликат
  маски правил в CLI пришлось синхронизировать, иначе отчёт по группе
  включал чужие строки (9984 строки вместо 3990).
- **Справочники — только данными.** Бизнес-правила лежат в JSON (`data/*.json`),
  читаются через `core.load_*` со встроенным фолбэком. Битый файл даёт WARN
  и фолбэк, а не падение.
- **Заливка в БД — одна функция** (DROP + CREATE + 3 индекса по контракту).
  Других путей записи в `catalog` нет.
- **Версионирование — только скриптом снапшотов** с именем
  `after_iter<N>`. Резервные копии рядом с кодом (`*_old.py`, `*.bak`)
  запрещены. Снапшот без номера итерации однажды дал коллизию имён,
  отсюда строгое правило именования.
- **Коммит и снапшот — только по запросу человека.**
- **Деструктивные операции** (удаление исходных прайсов и снапшотов,
  `DROP DATABASE`, любые действия вне папки проекта) — только с
  подтверждением. Старую БД первой версии не трогать.
- **Никакой автоматизации ввода на уровне ОС.** Однажды экранный клик агента
  попал в окно соседнего приложения (выделил текст, данные не изменились).
  С тех пор GUI проверяется только in-process (`event_generate`) или вручную.
- **Тест проверяет поведение, а не наличие.** Тест «секция существует» был
  зелёным, пока секция имела высоту 1 px и пользователь её не видел. Теперь
  тесты видимости проверяют геометрию (mapped, высота на окне 1280×800).
- **Перекалибровка теста** (изменение ожидаемого числа) допустима только со
  ссылкой на причину и на прецедент в журнале итераций.

## 3. pandas 3.0: обязательные паттерны

| Правило | Что ломалось без него |
|---|---|
| NaN → строка только через `.fillna("")` перед `.astype(str)` (или явный список с `pd.isna`) | литерал `"NaN"` попадал в БД как текст |
| `.map()` / `.apply()` на строковых колонках запрещены, только векторные операции | `None → NaN → "NaN"`, плюс скорость |
| Булевы маски на пустом df — `pd.Series(..., dtype=bool)` явно | `object`-маска на 0 строк возвращала DataFrame с **0 колонками**, ниже по цепочке `KeyError('Категория')` |
| Сравнение на колонках с NA — только после `fillna("")` | `startswith` на NA даёт NA, и индексация маской с NA падает |

## 4. Guard-условия алгоритма подбора

Guard — это условие, при котором алгоритм **честно отказывается** отвечать,
вместо того чтобы вернуть правдоподобный, но неверный результат.

| Guard | Что предотвращает |
|---|---|
| **Маршрутизация** (`has_criteria`): в строке есть «СНП», но не распознан ни один признак — запрос не уходит в точный подбор | пустой фильтр отдал бы **весь каталог** как «точное совпадение» |
| **Полнота ключей** кросс-аналогов: пара сравнивается, только если у обеих строк есть ВСЕ ключи размеров | у типа А в прайсе нет d1, а по двум ключам d2/d3 разные типоразмеры совпадают в допуске 1 мм: фантомные аналоги с другим DN |
| **Конфигурация, а не буква**: кросс-стандарт сравнивает конфигурацию колец (`core.TYPE_CONFIG`: NONE/INNER/OUTER/BOTH), а не букву типа | буква «В» у ГОСТ — внутреннее кольцо, у ASME — наружное; сравнение по букве даёт аналоги другой конструкции |
| **Два уровня кросс-аналогов**: «посадка» (размеры в допуске) отдельно от «номинала» (тот же DN, размеры вне допуска, пометка «проверить посадку») | совпадение номера DN между ГОСТ и ASME почти всегда означает другой физический размер |
| **Диагностика зеркалит фильтры** в том же порядке (полнота → конфигурация → допуск → материал); маркер «рассинхрон диагностики и фильтров» в норме не встречается, тест прогоняет ≥200 строк | объяснение «почему аналогов 0» не должно расходиться с реальной причиной |
| **Точный подбор строгий**: ближайшие варианты при промахе — отдельный уровень с причиной и тегом «требует подтверждения», вне суммы КП | «похожее» не должно тихо попадать в коммерческое предложение |
| **Аналоги вне суммы**: в заказе точные позиции идут в итог, аналоги — отдельным блоком | |
| **NULL-цена блокирует КП** («цена не задана — позиция только для подбора аналога») | раньше NaN тихо превращался в 0.00 ₽ в документе для клиента |
| **Давление обязательно для колец**: строка, у которой давление по смыслу есть, но не распознано, при заданном PN исключается | 35 колец без давления проходили любой фильтр PN |
| **Количество — не токен**: `12 кг`, `5 шт`, `x 3` вырезаются до разбора, сечение `6х6` количеством не считается | `шт` и число искались как часть маркировки, и заявка промахивалась |
| **Свёртка кода только расширяет выдачу** (`МГ 140` = `МГ-140` = `МГ140`); склейка «буквы + число» — только если свёрнутый код есть в каталоге | ложные совпадения по случайной подстроке (`…м С-500` → `МС500`) |
| **Токены правил — с учётом подстрок**: короткие коды (`АФ`, `НА`) исключены из правил после разведки | `АФ` ловил «грАФит», `НА` — каждое слово «НАбивка» |
| **Бренд «уже есть в каталоге»** проверяется по целым словам нормализованной маркировки, а не подстрокой | два разных кода одного класса эквивалентности склеивались в «дубль» |
| **Единая реализация правил поставщиков** (`group_row_mask`): одна функция вместо трёх копий в разных модулях | при добавлении нового поля копии расходились; в одной нашёлся скрытый баг пустого списка категорий |
| **Пустая группа ≠ «все строки»**: если у группы не осталось категорий, её удаляют или явно ставят несуществующую категорию с честным нулём | пустой список `categories` по семантике означает «любая категория» |

## 5. Процесс итерации

1. **Разведка**: запросы к живым данным, только чтение. Результат — числа,
   а не предположения.
2. **Правка** в границах задачи. Отклонение от границ явно описывается.
3. **Приёмка**: все тестовые наборы, регрессионная четвёрка, проверка
   инвариантов. Вывод урезан до последних 10–15 строк.
4. **Документация**: инварианты, реестр асимметрий (SELECTION_SPEC §2) и
   раздел итерации обновляются в том же изменении.
5. **Снапшот** `after_iter<N>` — по запросу человека.

Ответы агента — короткие: diff «было → стало», без дампов файлов, не больше
5 пунктов пояснения. Это тоже правило из файла: длинный отчёт после каждой
итерации никто не читает.

## 6. Известные ограничения (честный список)

- Бренд-аналог набивки подбирается по классу эквивалентности; сечение при
  выборе строки-аналога не учитывается (в демо на `AX 101 8х8` аналоги
  приходят сечением `10х10`).
- У типов СНП А/Б (конфигурация NONE) кросс-аналогов нет по построению
  (guard полноты): в прайсе нет второго надёжного размерного ключа.
- Класс ASME хранится в «кгс»-колонках ×10 (историческое кодирование
  рабочей БД, см. DB_SCHEMA.md) и сохранён ради совместимости ядра.
- Разбор списка позиций внутри одной ячейки заявки («СНП-А 1, СНП-Б 2»)
  не поддерживается: одна позиция — одна строка.
