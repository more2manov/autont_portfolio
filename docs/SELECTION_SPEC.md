# SELECTION_SPEC.md — спецификация подбора позиций (src)

> **Портфолио-версия.** Обезличенная копия рабочей спецификации подбора:
> поставщики заменены на `Vendor A..X`, торговые марки — на синтетические
> названия, ссылки на внутренние файлы и интеграции удалены. Номера итераций,
> разведки и цифры (например, «15 573 строки каталога») относятся к рабочему
> каталогу; демо-каталог портфолио — ~210 синтетических строк
> (`python build_mock.py`). `gui.py` входит в репозиторий в адаптированном
> виде (`src/gui.py`: SQLite вместо PostgreSQL, вкладка «Источники» —
> по данным демо, `python run_gui.py`); упоминания `entry.py` / `gui_tests.py`
> относятся к модулям рабочей версии, которые в репозиторий не входят;
> ядро (`src/matching.py`, `src/core.py`) — то же, что описано здесь.

Документ фиксирует, как заявка клиента (произвольная текстовая строка)
превращается в позиции каталога: карту алгоритма, реестр известных
рассогласований R1–R8 (что было исправлено/задокументировано и почему), и
таблицу намеренных асимметрий подбора — мест, где логика специально
выглядит несимметрично, чтобы не путать со «случайными» багами.

## 1. Карта алгоритма


## 2. Таблица асимметрий (намеренные, не баги)

| # | Место | Асимметрия | Обоснование |
|---|---|---|---|
| A1 | `pressure_hit` vs `pressure_range_hit` | Одиночное `pn` проверяется «входит ли в диапазон строки» (интервал строки фиксирован, точка запроса гуляет); диапазон запроса `pn_lo/pn_hi` проверяется на **пересечение** интервалов | Клиент в 90% случаев называет одно число (номинальное PN), но старые маркировки ОСТ хранят диапазон в самой марке (пример 2) — для них проверка «точка в диапазоне» не определена, нужна проверка пересечения двух диапазонов |
| A2 | Умолчание единиц давления: ОСТ → МПа×10, ГОСТ/прочее → кгс как есть | Асимметрично по стандарту, а не универсально | Исторически прайсы ОСТ печатают PN в МПа без пометки единицы, ГОСТ — в кгс/см²; угадать без привязки к стандарту нельзя (пример 2) |
| A3 | `resolve_customer`/`find_snp`: толщина — **точное** совпадение (`abs(Δ) < 1e-9`) | `find_smart_analogs`: толщина — допуск **±`core.THICKNESS_GUARD` (1.3 мм)** | Точный подбор обязан отдавать РЕАЛЬНО существующую в прайсе позицию; допуск существует только в подборе АНАЛОГОВ, где «требуется подтверждение» менеджера — смешивать нельзя, иначе точная таблица «подберёт» несуществующую толщину без предупреждения |
| A4 | `find_cross_analogs`: категория ФИКСИРОВАНА (== категория исходной строки), меняется только стандарт | `find_brand_analogs`: категория ФИКСИРОВАНА на `"Набивки"`, меняется бренд | Кросс-стандартная замена (СНП/Овальные) имеет смысл только внутри одной товарной формы (кольцо на кольцо); брендовая замена — только внутри набивок (там есть `core.BRAND_GROUPS`) — категории не смешиваются никогда |
| A5 | Дюймовая метка (`INCH_RE`) даёт `dn` только при `std` пустом или `"ASME"` (R6) | Для ГОСТ/ОСТ дюймы никогда не парсятся, даже если в строке случайно есть `"` | ДЮЙМЫ — система измерения ASME B16.20; ГОСТ/ОСТ — метрическая; ложное совпадение кавычки в строке ГОСТ-заявки не должно подменять DN |
| A6 | Хвостовое число — количество, ТОЛЬКО если отделено пробелом (R7); число, слитное через дефис с маркировкой — часть маркировки | `"...250-16"` → qty не трогаем; `"...250-16 2"` → qty=2 | В маркировках дефис — разделитель размеров/давления (не разделитель заявки от количества); только явный пробел в конце означает «а вот это отдельно посчитанное количество» |
| A7 | Сравнение маркировки (`resolve_customer`/`diagnose_miss`) — ТОЛЬКО префикс, нечувствительный к пробелам/дефисам (`_norm_mark_cmp`/`_norm_mark_series`: UPPER + схлопнуть `[\s\-]+`); защиты «не зацепить лишнее» на уровне самого сравнения НЕТ | `"СНП-Д-3-28"` находит каталожное `"СНП Д-3-28-(Ру)-(h)"` (пример 9); потенциально зацепил бы и `"СНП Д-3-280…"`, если бы такая маркировка существовала | От ложных префиксов защищает НЕ нормализация маркировки, а СЛЕДУЮЩИЙ фильтр `DN_num == cust["dn"]` в том же `resolve_customer` — маркировка в прайсе пишется то дефисом, то пробелом (реальный промах менеджера, итерация 16, см. §6), различать разделители не имеет смысла, а ложный префикс всё равно отсеет DN |
| A8 (изменена итерацией 27) | `resolve_customer`: fullmetal-строки (`"как навитая"` в `Маркировка_в_прайсе`) по умолчанию НЕ отфильтровываются — обе ценовые группы показываются вместе. Единственное сужение: если `"как навитая"` есть в самой заявке (`cust["raw"]`) — оставляем ТОЛЬКО fullmetal-строки | ГОСТ Г/Д даёт 2 строки на вариант (обычная цена + fullmetal дороже) — это ДВА РАЗНЫХ ПРОДУКТА (разный материал ограничителя, колонки прайса H–K/L–O), не дубль одной позиции (см. §7, итерация 27; было отменено скрытие итерации 17, которое ошибочно трактовало это как дубль) | «как навитая» (не полный `core.GROUP_FULLMETAL` со скобками) — та же подстрока, что уже использует `check.py` для классификации строк каталога; менеджер копирует либо суть, либо полную маркировку из каталога/КП (там хвост присутствует целиком) — оба случая ловятся. Различимость групп в GUI — колонка «Ограничитель» (`matching.restrictor_kind`) |
| A9 | `find_smart_analogs`: `relaxed = dict(cust, steel=None, thickness=None)` — сталь/толщина обнуляются для каскада аналогов, а `dn`/`pn`/`pn_lo`/`pn_hi`/`std`/`type` НЕТ | Аналог с другим давлением/размером никогда не предлагается, даже если по стали/толщине идеально подходит | Давление и размер — предохранительный критерий (несовместимое по давлению уплотнение — это авария, не «почти то же самое»); сталь и толщина — заменяемые параметры (апгрейд/допуск ±1.3мм), релаксация которых прямо documented в A3 |
| A10 | Одна позиция каталога = одна строка заявки; `parse_request_file`/журнал (`history.append_entry`) не разбивают и не объединяют строки — многострочная вставка (список через запятую/точку с запятой в одной ячейке) читается как ОДНА нераспознанная строка | `"СНП-А 1, СНП-Б 2"` в одной ячейке экспорта — НЕ две позиции, а один непарсящийся `mark` | Разбор списка внутри строки — отдельная, не решённая задача (неоднозначность, где кончается одна позиция и начинается другая, без явного разделителя строк); импорт (итерация 14) и журнал (итерация 15) сознательно требуют «одна позиция — одна строка/одна ячейка», как в реальных КП-файлах |
| A11 | `search_generic`/`diagnose_search`: токены короче 2 символов (`len(t) >= 2` при разбиении по `[\s,;]+`) отбрасываются целиком, включая однобуквенные | Запрос `"а 101"` ищет только по токену `"101"`, `"а"` не участвует в фильтре и не считается «ненайденным» | Однобуквенные и пустые токены (предлоги, опечатки, лишние разделители) — шум: без порога `search_generic` тривиально матчил бы любую строку каталога, содержащую распространённую букву |
| A12 | `search_with_criteria` (итер. 18): распознанные dn/pn(_range)/steel/thickness применяются как ФИЛЬТРЫ по колонкам (`DN_num`/`Давление_кгс_*`/`Материал`/`Толщина / Высота`), а НЕ как токены, которые обязаны буквально встретиться в hay (Маркировка+SKU+Материал+Категория). Пустой остаток токенов ПОСЛЕ вычитания критериальных фрагментов (`_remaining_tokens`) — это не промах, а успех: «вся заявка — это критерии» | `"DN250 PN16 2"` (реальная строка боевого журнала) находит 67 строк каталога (с итерации 50 — 32: 35 колец проходили фильтр давления без давления в кгс, §19), хотя ни `"dn250"`, ни `"pn16"` не встречаются в hay буквально ни в каком виде | `search_generic` не видит давление/DN как числа вообще (это была топ-причина промахов аудита боевого журнала — итерация 17 → 18, см. журнал `request_history.json`); строка без mark/type/«СНП» не может уйти в `resolve_customer` (нет структурного якоря-категории), но структурные критерии всё равно должны фильтровать, а не искаться подстрокой |
| A13 | `find_cross_analogs` (итер. 19): ключи сравнения размеров у СНП зависят от ТИПА (`core.cross_keys_for`) — тип А сравнивается по (d1, d2), типы В/Г/Д — по (d2, d3), плюс d4, если он есть в ОБЕИХ сравниваемых строках. У типа А в этом прайсе d1 в `Основные_размеры` не встречается НИ РАЗУ — поэтому guard полноты отсекает кросс-аналоги типа А целиком (0 всегда), а не потому, что для типа А это «отдельный случай» в коде | `"Прокладка СНП-А-2-3-25-25"` (ГОСТ, DN25) раньше давала кросс-«аналог» `"СНП А-3-43"` (ОСТ, DN43, см. §8); теперь — 0 кросс-аналогов | У типа А нет наружного уплотняющего кольца — d2/d3 (внутренние посадочные диаметры) сами по себе недостаточно дискриминативны и совпадают в допуске 1.0 мм у РАЗНЫХ DN (см. диагностику §8); у В/Г/Д третье независимое измерение (d1, часто и d4) делает совпадение по d2/d3 надёжным сигналом даже когда числовые метки DN/ОСТ-SIZE у стандартов расходятся на десятки (см. §8 — это НЕ брак, а разные системы нумерации типоразмера у ГОСТ и ОСТ) |
| A14 | Точный подбор (`resolve_customer`/`search_generic`/`search_with_criteria`) vs `nearest_variants` (итер. 41) | Точный подбор строгий (все токены/фильтры, AND); ближайшие варианты — по семейству кода (префикс ≥2 букв + цифра) и близости сечения, вне суммы, с пометкой «требуют подтверждения» | Код без строки в каталоге (напр. RK-240I) — не точная позиция: аналог/семейство только подсказка менеджеру, цена и совместимость не гарантированы (§18) |

## 3. Реестр рассогласований R1–R8

| # | Название | Что было не так | Где исправлено |
|---|---|---|---|
| **R1** | Guard `has_criteria` в `entry.cmd_order` | Позиция без единого распознанного признака (dn/pn/mark/толщина/сталь) всё равно резолвилась — глобальные `type`/`std`/`thickness`/`steel` заказа (одинаковые для ВСЕХ позиций) сами по себе делают `has_criteria` истинным после `.update()`, и `resolve_customer` тихо отдавал первую строку широкого фильтра «весь тип+стандарт» как будто это заказанная позиция | `entry.cmd_order`: проверка `has_criteria` на СЫРОМ `cust` (до `.update()`), промах — с причиной, вне суммы (итерация 12) |
| **R2** | Токено-диагностика search-промахов | Промах `search_generic` не объяснялся вообще (`diagnose_miss` зеркалит фильтры `resolve_customer` и для токенного поиска бессмыслен) | `matching.diagnose_search(df, line)`: ненайденные токены + топ-3 кандидата; подключена в `entry.cmd_search` (итерация 12) **и в `gui.OrderTab`** — промахи search-пути, кнопка «Почему не найдено?», статус-строка (итерация 13). **ЗАКРЫТ.** |
| **R3** | Асимметрия допуска толщины (точная/±1.3мм) | Не баг, но выглядит несимметрично без объяснения | Задокументировано в §2 (A3); код — `core.THICKNESS_GUARD`, итерация 7 |
| **R4** | Синонимы токенов поиска | «набивка» (ед.ч.) не входит подстрокой в категорию «Набивки»; «ф-4»/«фторопласт» изначально (итерация 12) были заведены на всю категорию «ПТФЭ» — но эта категория содержит РЕЗИНОВЫЕ и прочие посторонние материалы (МБС и др.), которые category-wide синоним ошибочно подмешивал в выдачу «ф-4» | `core.SYN_TOKENS` + `matching._syn_mask`, подключено в `search_generic`/`diagnose_search` (итерация 12); **поправка итерации 13 (задача 0)**: «ф-4»/«фторопласт» переведены на условие по МАТЕРИАЛУ (`("Материал", ("PTFE", "Ф-4"))`), а не по категории — резиновые материалы больше не просачиваются |
| **R5** | Асимметрия единиц/умолчаний давления (ОСТ↔ГОСТ, МПа↔кгс) | Не баг, но источник постоянных вопросов | Задокументировано в §2 (A1/A2); код — итерации 9/9.2 |
| **R6** | Дюймы только для ASME/пустого std | `INCH_RE`-фолбэк применялся независимо от `std` — случайная кавычка/дробь в ГОСТ/ОСТ-заявке могла подменить DN дюймовым пересчётом | `parse_customer_line`: `elif cust["std"] in (None, "ASME")` перед `INCH_RE.search` (итерация 12) |

## 6. Реальный промах (сравнение маркировок), итерация 16

Строка `"Прокладка СНП-Д-3-28-1,6-3,2 ОСТ26.260-454-99"` давала «фильтр
«маркировка» обнулил подбор», хотя позиция в каталоге есть
(`"СНП Д-3-28-(Ру)-(h)"`, ОСТ). Две независимые причины, обе исправлены:

1. **Сравнение маркировки нормализовало только пробелы.** Заявка написана
   через дефис (`СНП-Д-3-28`), каталог — через пробел (`СНП Д-3-28`);
   `str.replace(" ", "")` с обеих сторон давал `"СНП-Д-3-28"` (заявка,
   дефис остался) против `"СНПД-3-28-(РУ)…"` (каталог, дефис после «Д»
   остался, но пробела после «СНП» уже не было) — `startswith` ложно
   возвращал `False`. Новые `matching._norm_mark_cmp` (скаляр,
   `cust["mark"]`) и `matching._norm_mark_series` (векторно, колонка
   каталога) схлопывают ОБА разделителя (`re.sub(r"[\s\-]+", "", ...)`) —
   единственная функция для обеих сторон сравнения, применяется в
   `resolve_customer` и `diagnose_miss`/`_miss_apply_step` (шаг
   «маркировка»). Защита от ложных префиксных совпадений — см. §2 A7:
   это НЕ зона ответственности нормализации, а следующий по цепочке
   фильтр `DN_num == cust["dn"]`.
2. **`STD_NUM_RE` не покрывал слитную/гибридную запись номера стандарта.**
   `"ОСТ26.260-454-99"` (без пробела перед номером, дефис вместо второй
   точки) не масковался: `\b` перед `\d+` не срабатывал (между кириллической
   буквой и цифрой в Unicode-режиме `re` нет word-границы — обе `\w`), а
   `(?:\.\d+){2,}` требовал ВСЕ разделители строго точками. Новый паттерн —
   `(?<!\d)\d+\.\d+(?:[.\-]\d+)+\b`: ведущий `(?<!\d)` вместо `\b` допускает
   слитное написание с буквой перед числом; ПЕРВЫЙ разделитель после
   начального числа обязан быть точкой (иначе замаскировались бы и обычные
   дефисные маркировки СНП вида `"2-3-250-16"`, где точек нет вовсе — это
   была бы регрессия), дальше — точка ИЛИ дефис, что покрывает все три
   заданных формата (`26.260.454-99`, `26.260-454-99`, `26.260.454.99`) и
   их слитное присоединение к слову стандарта. Детекция `std` сама по себе
   не пострадала бы и без этого фикса (она ищет `"ОСТ"` через `in` —
   подстроку, не regex), но без маскировки числа его куски (`26`, `260`,
   `454`, `99`) остаются в `work` и рискуют попасть в другие regex дальше
   по цепочке на иных входных строках.

## 7. Fullmetal-группа СНП: две цены — два продукта, не дубль (итерация 17, правило скрытия ОТМЕНЕНО итерацией 27)

**Правило итерации 17 (отменено).** Аудит боевого журнала показал: у ГОСТ
Г/Д `resolve_customer` систематически отдаёт ДВЕ строки на вариант —
обычную и `"(ограничитель как навитая часть)"` (дороже, см. бывший A8) —
и это трактовалось как дубль одной позиции. Фикс скрывал одну из групп по
умолчанию (обычную — если в тексте заявки не было слова «навитая»).

**Почему это было неверно (разведка итерации 27).** Реальный кейс:
`СНП-Г-В-В-10-40 ГОСТ Р 52376-2005` резолвится в 4 позиции, а исходный лист
прайса `СНП-ГОСТ-Г` для DN10 PN10.0-40.0 содержит **восемь** цен — 4 стали
× 2 колонки-группы: H–K «с ограничителем из углеродки» (49/53/70/98) и L–O
«с ограничителем как навитая часть» (74/75/118/160). Это не одна и та же
физическая деталь по двум ценам — это ДВА РАЗНЫХ ПРОДУКТА (разный материал
ограничителя), и прайс всегда предлагает клиенту выбор между ними. Скрытие
итерации 17 отдавало менеджеру только один из двух легитимных вариантов
подбора, не «дедуп дубля».

Разведка `groupby(('Стандарт','Тип_изделия'))` по категории «СНП»
(`Маркировка_в_прайсе` содержит `"как навитая"` = вторая группа) —
**пересчитана итерацией 34** (задание ПРОМТ 34, п. «пересчёт §7»): у
категории «СНП» ровно один источник (`Источник` = `PR2`, Price2.xlsx —
второго прайса с этими данными не существует, деление «для обоих прайсов»
из задачи 34 на эту категорию не ложится, см. ниже):

| Стандарт | Тип | fullmetal-строк | обычных строк | наружное кольцо (`core.TYPE_CONFIG`) |
|---|---|---:|---:|---|
| ГОСТ | Г | 472 | 472 | OUTER |
| ГОСТ | Д | 408 | 408 | BOTH |
| ГОСТ | А, В | 0 | 576 / 136 | NONE / INNER |
| **ОСТ** | **Г** | **880** | **880** | OUTER |
| **ОСТ** | **Д** | **880** | **880** | BOTH |
| ОСТ | А, Б, В | 0 | 792 / 568 / 640 | NONE / NONE / INNER |
| ASME | В, Г | 0 | 280 / 2272 | OUTER |
| ASME | Д | 0 | 2184 | BOTH |
| ASME | А | 0 | 584 | NONE |

**Исправление итерации 34.** Прежняя редакция этого раздела (итерация 27)
утверждала «две ценовые группы есть только у ГОСТ Г/Д» и «у ОСТ Г/Д и
ASME В/Г/Д альтернативы «как навитая» в прайсе нет вовсе» — это было
**фактически неверно для ОСТ**: пересчёт живого каталога (итерация 34,
задача 0в) показал, что у ОСТ Г и ОСТ Д fullmetal-суффикс присутствует
РОВНО ТАК ЖЕ, как у ГОСТ Г/Д — ровно половина строк каждой пары (880 из
1760). Верно лишь для ASME: у ASME В/Г/Д наружное кольцо тоже есть
(`OUTER`/`BOTH`), но альтернативы «как навитая» в прайсе действительно нет
— там всегда одна цена, «из углеродки». Итоговое правило: **fullmetal-
суффикс существует у ГОСТ Г/Д И ОСТ Г/Д, но не у ASME** (даже там, где
`TYPE_CONFIG` даёт тот же `OUTER`/`BOTH`) — `TYPE_CONFIG` предсказывает
только НАЛИЧИЕ наружного кольца как физической детали, а не то, продаёт ли
конкретный прайс-лист обе ценовые группы по нему. У типов без наружного
кольца (`NONE`/`INNER`) ограничителя нет вовсе. Код `matching.
restrictor_kind` (ниже) все эти четыре стандарто-типа уже обрабатывал
правильно и раньше (проверка «как навитая» в маркировке идёт первым шагом,
независимо от стандарта) — ошибка была только в тексте этого раздела, не в
поведении программы, править `matching.py` не потребовалось.

**Новое правило (итерация 27).** `resolve_customer` (обе ветки — mark и
симметричная type-без-mark для joint-строк, итерация 26) по умолчанию
**показывает обе группы**, ничего не скрывая. Единственное исключение —
прежнее, НАМЕРЕННОЕ требование: если само слово «как навитая» есть в
тексте заявки (`cust["raw"]`), подбор сужается ТОЛЬКО до fullmetal-строк
(клиент явно просил этот вариант). Симметричного сужения «только обычные»
по умолчанию больше нет.

**Различимость — колонка «Ограничитель».** Раз обе группы теперь видны
одновременно, менеджеру нужен способ отличить их в таблице без чтения
полной маркировки. `matching.restrictor_kind(row)`:
1. `"как навитая"` в `Маркировка_в_прайсе` → `"как навитая часть"`;
2. иначе `core.TYPE_CONFIG[(Стандарт, Тип_изделия)]` ∈ `{OUTER, BOTH}` →
   `"из углеродки"` (наружное кольцо есть, но в этом листе прайса только
   одна цена — ОСТ Г/Д, ASME В/Г/Д);
3. иначе → `"без ограничителя"` (`NONE`/`INNER`, либо категория вне «СНП»).

Колонка добавлена в `gui.RESULT_COLS` (обе таблицы — точные позиции и
аналоги; `gui._fmt_cell` вызывает `restrictor_kind` только для рендера,
данные каталога не меняются). Агрегаты родительской строки дерева и
`sort_for_manager` колонку игнорируют — группировка и сортировка
по-прежнему по SKU/цене, а не по ограничителю.

**Честное предупреждение об изменении поведения.** Отмена скрытия — не
point-fix, а общее правило внутри `resolve_customer`: у ЛЮБОЙ заявки без
явного «как навитая», резолвящейся в ГОСТ Г/Д **или ОСТ Г/Д** (уточнено
итерацией 34 — таблица выше показала, что ОСТ Г/Д ведёт себя так же, как
ГОСТ Г/Д, это не было отдельно проверено в итерации 27), число строк
подбора теперь РОВНО ВДВОЕ больше, чем было при действовавшем в итерациях
17–26 правиле (репро-строка §12 — 8 строк вместо 4, ГОСТ). Это ожидаемое и
желательное следствие фикса (обе группы — легитимные позиции, которые
раньше терялись для половины заявок), а не регрессия. У типов, где
fullmetal-группы нет (В, ASME Г/Д и т. д.), поведение не меняется.

## 8. Кросс-аналоги СНП: типовые ключи + guard полноты, итерация 19

**Диагностика (уточняет исходную формулировку промаха).** Задача
предполагала, что у типа А отсутствует ключ `d3` в `Основные_размеры`, и
поэтому сравнение «вырождается» (отсутствующий ключ совпадает сам с
собой). Прямая проверка `core.norm_dims` на живом каталоге это
опровергает: `d3` у типа А ЕСТЬ всегда, и уже ДО этой итерации `ok()`
в `find_cross_analogs` явно исключала кандидата, если ключа нет
(`if k not in d: return False`) — guard «отсутствующий ключ = пропуск»
для d2/d3 фактически уже существовал. Настоящая причина другая:

```
ГОСТ А DN25 (SS304, вар. давления 10.0-160.0): d2=42.0, d3=58.0
ОСТ  А DN43 (SS304):                            d2=43.0, d3=57.0
  |Δd2| = 1.0 мм (в допуске CROSS_TOL=1.0), |Δd3| = 1.0 мм (в допуске) -> ЛОЖНОЕ совпадение

ГОСТ А DN32 (SS304, вар. давления 10.0-160.0): d2=50.0, d3=66.0
ОСТ  А DN51 (SS304):                            d2=51.0, d3=65.0
  |Δd2| = 1.0 мм, |Δd3| = 1.0 мм -> тоже ложное совпадение (симметричный случай)
```

У типа А только 2 измерения (d2/d3, внутренние посадочные диаметры — нет
наружного уплотняющего кольца), и у этого прайса шаг типоразмеров ГОСТ/ОСТ
для типа А достаточно мелкий, чтобы соседние по факту РАЗНЫЕ DN попадали
в допуск 1.0 мм одновременно по обоим ключам. Два ключа — недостаточная
дискриминация, а не «отсутствующий ключ».

**Фикс.** `core.cross_keys_for(cat, typ)`: тип А -> `(d1, d2)`; типы
В/Г/Д -> `(d2, d3)`, плюс `d4`, если он есть в ОБЕИХ строках пары
(доп. уточнение посадки внешнего кольца, когда данные это позволяют).
В этом прайсе `d1` у типа А не встречается ни в одной строке — поэтому
guard полноты (`any(k not in base for k in keys)`) отсекает кросс-аналоги
типа А целиком: это осознанный побочный эффект отсутствия у типа А
надёжного второго дискриминирующего измерения в справочнике размеров, а
не хардкод «для типа А всегда 0» в коде.

**Честное предупреждение (аналогично §7).** Приёмочное ожидание
«кросс-аналоги СНП-В-2-3-250-16 ГОСТ — только с |ΔDN| ≤ 8» не
подтвердилось на живых данных и было пересмотрено. Живой пример:
`СНП-В-2-3-ГОСТ-DN250` (SS304, вар. давления 10.0-160.0, d1=279/d2=291/
d3=313) даёт корректный кросс-аналог `СНП-В-ОСТ-SIZE292` (d1=280/d2=292/
d3=312 — **все три** измерения расходятся не больше чем на 1.0 мм), при
том что `DN_num` расходится на 42 (250 против 292). Причина —
`DN_num` берётся как первое число из колонки «DN / Размер»
(`catalog.py`, `re.search(r"\d+", ...)`) буквально из текста прайса; для
ГОСТ это нормальный номинальный DN, а для ОСТ — собственная «SIZE»-метка
стандарта (видно уже в SKU: `SNP-В-ОСТ-SIZE292…`), которая физическому
DN не равна и не обязана быть близкой к нему. Проверка по всему каталогу
подтверждает, что это системное свойство данных, а не единичный случай:
у типов В/Г/Д, где кросс-аналоги корректны (все дискриминирующие
измерения совпадают в допуске 1.0 мм), фактический разброс `|ΔDN_num|`
лежит в диапазоне 22–51 (медиана 25–41 в зависимости от типа) — то есть
«скачок номера» — это НОРМА для валидных кросс-пар этого прайса, а не
признак фантомного совпадения. Признак фантома — как раз-таки продемон-
стрированный в типе А случай, когда ФИЗИЧЕСКИЕ размеры (а не номер)
совпадают лишь СЛУЧАЙНО при недостаточном числе дискриминирующих ключей.
Фильтр по `|ΔDN_num|` поэтому в код не добавлен — он не различает
«число совпало случайно на 2 ключах» (реальный баг) и «число другое,
потому что у стандарта другая система нумерации» (норма), и его
добавление лишило бы кросс-аналогов почти весь каталог типов В/Г/Д.

## 9. Дубли строк заявки, итерация 21

**Семантика.** У СНП давление хранится ДИАПАЗОНОМ каталожной строки
(«10.0–160.0» кгс — см. `pressure_hit`/`pressure_mask`, §2 A1), а не точкой.
Поэтому ДВЕ РАЗНЫЕ строки заявки с разным номинальным давлением (например,
«…-50-25» и «…-50-16» — 25 и 16 кгс) могут обе попасть в один и тот же
диапазон одной и той же каталожной строки и зарезолвиться в ОДИН и тот же
набор SKU. Это не ошибка резолва — диапазон каталога действительно
покрывает оба запроса — но менеджер видит две отдельные группы в дереве, не
подозревая, что это, по сути, один и тот же товар. Дубль — свойство ЗАЯВКИ
(два разных способа описать одну и ту же каталожную позицию), а не свойство
каталога: в каталоге ничего не задваивается, задваивается предложение
менеджера, если оба варианта попадут в КП независимо.

**Обнаружение (gui.on_resolve).** Отпечаток группы — `frozenset(SKU всех
детей)`, без учёта порядка и количества повторов. Группы перебираются в
порядке `matching.group_by_line` (порядок ввода заявки); первое вхождение
отпечатка — не дубль, каждое следующее — дубль ПЕРВОГО (не предыдущего:
если строки 5/6/7 дают одинаковый отпечаток, и 6, и 7 помечаются «дубль
строки 5», а не 7 — «дубль строки 6»; так проще проследить первоисточник).
Метка ставится ТОЛЬКО на родителя дерева (`" — дубль строки N"` после
разбивки по категориям, если она есть, см. A12) — дети, их сортировка
(`sort_for_manager`) и агрегаты родителя (цена/остаток) не меняются: дубль
— это ярлык для менеджера, не фильтр, скрывающий позиции.

**Защита КП (`matching.merge_or_append_kp`).** Дубль строк заявки — не
единственный путь получить один SKU в предложении дважды (менеджер может
добавить его вручную из разных групп, точной таблицы и аналогов). Поэтому
защита стоит на границе добавления В КП, а не только на детекте групп:
`_add_to_kp` проверяет наличие SKU в `self.kp_items` ДО вызова хелпера и,
если он уже есть, спрашивает подтверждение (`askyesno`) — «да» сливает
количество в СУЩЕСТВУЮЩУЮ строку (её цена и прочие поля не переписываются
данными нового добавления — специально, чтобы повторное добавление той же
позиции не исказило уже согласованную строку КП другой ценой того же
товара), «нет» отменяет добавление целиком (не создаёт
вторую строку и не меняет существующую). Без дубля — диалога нет, поведение
как раньше.

## 10. Заявки ANSI/ASME, итерация 22

**Разведка (что реально хранит каталог).** Лист «ASME B 16.20» (Price2.xlsx)
хранит колонку давления («Ру, (МПа)» — заголовок неточный, реально это
НОМЕР КЛАССА ANSI, не МПа) как одиночное число (`150`, `2500`) либо
текстовый диапазон `(300....600 )` — буквально то же обозначение, что
клиент написал как «КЛАСС ДАВЛЕНИЯ 300-600». Маркировка типа Г/Д собирается
как `"СНП <тип> <лицо фланца> <дюйм>\" CL<класс[-класс]>"` (пример:
`"СНП Г RF 3\" CL300-600"`, SKU `SNP-Г-ASME-RF-3in-CL300-600-SS304-H3.2`) —
без слова «ANSI»/«ASME» внутри самой маркировки (стандарт живёт отдельно, в
колонке «Стандарт»). `catalog.py` кодирует токен класса в
`Давление_кгс_мин/макс` тем же правилом ×10, что применяет к МПа→кгс у ОСТ
(проверено по всем 5320 ASME-строкам с «CL…» в `PN / Давление` — 0
расхождений): `CL300-600` → `Давление_кгс_мин=3000, Давление_кгс_макс=6000`.
Это НЕ инженерная psi/кгс-таблица (для той уже есть `core.PN_TO_CLASS`, но
она в обратную сторону и на порядок величины меньше того, что реально лежит
в БД) — `core.ANSI_CLASS_TO_KGS` намеренно зафиксирован под ФАКТИЧЕСКОЕ
кодирование каталога, а не под «правильную» ANSI-таблицу, иначе фильтр
давления не нашёл бы ни одной реальной строки.

**Реальный промах и уточнённый диагноз.** Заявка `"...СНП-Г-3-ANSI-RF-3"-
(РУ)-(H)КЛАСС ДАВЛЕНИЯ 300-600 D2-101,6(ММ), D3-120,7(ММ), D4-149,4(ММ) -
4 шт."` давала «фильтр „DN" обнулил подбор». Причина в ДВЕ ступени: (1)
`MARK_RE` матчит только `"СНП-Г-3"` — «3» здесь номер ИСПОЛНЕНИЯ (как у
ГОСТ `"СНП-А-2-3-…"`), не DN, — и это число попадало в `cust["dn"]`; (2)
дюймовый токен `3"` стоит ДАЛЬШЕ в строке, за нераспознанным «-ANSI-», и
старый код применял дюймовый пересчёт только когда `dn` ЕЩЁ не задан
(`elif`) — а он уже был (неверно) задан шагом (1), так что дюйм молча
игнорировался.

**Разбор (`parse_customer_line`).** «ANSI» — синоним `std="ASME"`
(служебные токены лица фланца — RF/FF/RJ/RTJ/STG/LTG/…, из того же набора,
что `parsers.py::_ASME_FLANGE` — на детект std не влияют). Дюймовый DN
теперь вычисляется ПОСЛЕДНИМ шагом разбора и ПЕРЕБИВАЕТ dn, выставленный
`MARK_RE` из усечённой маркировки (но НЕ перебивает явный `DN N`/`ДУ N` —
у него по-прежнему приоритет). «КЛАСС ДАВЛЕНИЯ X[-Y]» → `class_lo`/
`class_hi` (только известные классы — 150/300/400/600/900/1500/2500, чтобы
«КЛАСС ДАВЛЕНИЯ 900 - 2 шт.» без размеров между классом и количеством не
дочитывал «-2» как верхнюю границу диапазона). `D2-101,6(ММ)`/`D3-…`/`D4-…`
→ `dims_req` (запятая → точка через `_num`). Когда дюймовый шаг сработал и
маркировка была ASME — префикс `cust["mark"]` пересобирается в формат
каталога (`"СНП-<тип>-<лицо>-<дюйм>\""`), иначе `"SNPГ3"` из усечённого
матча не совпал бы префиксом ни с одной строкой каталога (`"SNPГRF3\"…"`).

**Приоритет размеров над DN (`resolve_customer`/`diagnose_miss`).** Если
`dims_req` содержит ≥2 ключей — фильтр по `dn`/`DN_num` НЕ применяется
вовсе, вместо него — совпадение `core.norm_dims(Основные_размеры)` по ВСЕМ
ключам `dims_req` в допуске `core.CROSS_TOL` (`matching.dims_mask`, тот же
паттерн без `.map()` на str-колонке, что `pressure_mask`/`pressure_range_mask`
— список по `df.iterrows()`). Обоснование: у ANSI одному дюймовому DN
соответствуют РАЗНЫЕ исполнения (STG/LTG и т.п.) с разными посадочными
размерами — размеры, которые клиент реально измерил на месте, точнее
номинального DN, округлённого до дюйма. Класс давления — фолбэк ТОЛЬКО
когда PN не задан явным числом (та же приоритетность, что pn_lo/hi → pn →
class_lo в `resolve_customer`): переводится в кгс через `core.ANSI_CLASS_TO_KGS`
и сравнивается через `pressure_range_mask` — тем самым диапазон `CL300-600`
и одиночный `CL900` обрабатываются одним и тем же кодом, а строки без
давления (как у остальных ASME-позиций) по-прежнему проходят всегда.

## 11. Кросс-стандарт СНП, итерация 23

**Проблема.** Заявка `Прокл.СНП Б-3-477-1,6-4,5 ОСТ26.260.454 — 60шт`
резолвится точно (8 строк ОСТ DN477), но «Аналоги (кросс-стандарт)» для
выделенной строки (ОСТ, тип Б, DN477, SS304, 4.5) = 0. Старый
`find_cross_analogs` требовал совпадения буквы `Тип_изделия` между
кандидатами разных стандартов — гипотеза итерации 23: буква типа не
одинакова по СМЫСЛУ (составу колец) между ГОСТ/ОСТ/ASME.

**Разведка: буква → конфигурация колец по стандартам.** Для каждой пары
(Стандарт, Тип_изделия) категории «СНП» — объединение ключей
`core.norm_dims(Основные_размеры)`, встреченных хотя бы у одной строки
(построчный `catalog.build_catalog()`, категория «СНП», 15 065 строк):

| Стандарт | Тип | Ключи в прайсе | Конфигурация |
|---|---|---|---|
| ГОСТ | А | d2,d3 | NONE |
| ГОСТ | В | d1,d2,d3 | INNER |
| ГОСТ | Г | d2,d3,d4 | OUTER |
| ГОСТ | Д | d1,d2,d3,d4 | BOTH |
| ОСТ | А | d2,d3 | NONE |
| ОСТ | Б | d2,d3 | NONE |
| ОСТ | В | d1,d2,d3 | INNER |
| ОСТ | Г | d2,d3,d4 | OUTER |
| ОСТ | Д | d1,d2,d3,d4 | BOTH |
| ASME | А | d2,d3 | NONE |
| ASME | В | d2,d3,d4 | OUTER |
| ASME | Г | d2,d3,d4 | OUTER |
| ASME | Д | d1,d2,d3,d4 | BOTH |

Вывод: буква «Б» существует только в ОСТ и по составу колец совпадает с
«А» (NONE) во всех трёх стандартах — не отдельная конфигурация, а
ОСТ-специфичное деление внутри NONE (вероятно, по лицу фланца/типу
прокладки, не по кольцам — за пределами разведки этой итерации). Буква
«В» — INNER у ГОСТ/ОСТ (внутреннее кольцо d1), но OUTER у ASME (наружное
кольцо d4, как «Г») — РАЗНЫЙ смысл одной и той же буквы между стандартами.
`core.TYPE_CONFIG[(std, type)]` фиксирует это отображение; сравнивать
кандидатов нужно по значению конфигурации, а не по ключу буквы.

**Топ-5 кандидатов другого стандарта для репро-строки** (ОСТ Б DN477
SS304 4.5, `norm_dims` = `{d2: 477.0, d3: 523.0}`, конфигурация NONE),
по сумме `|Δd2|+|Δd3|` среди всех букв других стандартов:

| Стандарт | Тип | Конфигурация | DN | d2 | d3 | Δd2 | Δd3 |
|---|---|---|---|---|---|---|---|
| ASME | Г | OUTER | 450 | 474.7 | 527.1 | 2.3 | 4.1 |
| ASME | Д | BOTH | 450 | 474.7 | 527.1 | 2.3 | 4.1 |
| ASME | Г | OUTER | 450 | 469.9 | 527.1 | 7.1 | 4.1 |

Ближайшие кандидаты по размеру (Δd2+Δd3 = 6.4 мм) — ASME тип Г/Д, у
которых конфигурация OUTER/BOTH, а не NONE репро-строки: физически это
прокладки С кольцом (усиленные), а не эквивалент плоской ОСТ-Б без колец.
Строк ASME/ГОСТ с конфигурацией NONE (тип А) и размерами d2/d3 в
окрестности 477/523 в этом прайсе нет вовсе — для этого типоразмера
эквивалента другого стандарта физически не существует.

**Выбранное ветвление: (a) сравнение по конфигурации через
`core.TYPE_CONFIG`.** У пар, где кандидат другого стандарта СУЩЕСТВУЕТ с
той же конфигурацией и размерами в допуске `core.CROSS_TOL` (пример
регрессии: СНП-В-2-3-250-16 ГОСТ ↔ ОСТ, конфигурация INNER — кросс
по-прежнему находит совпадение, теперь через конфигурацию, а не через
случайное совпадение буквы). У репро-строки (ОСТ Б, NONE) реальных
кандидатов NONE другого стандарта с размерами в допуске 1.0 мм нет —
`find_cross_analogs` возвращает 0, это корректный результат, а не баг.
`core.CROSS_TOL_XSTD` НЕ вводился: расхождение репро-кандидатов (2.3+4.1 мм)
получено при несовпадающей конфигурации (OUTER/BOTH ≠ NONE) — ослаблять
допуск здесь означало бы предлагать менеджеру прокладку с кольцом взамен
плоской, а не более широкий, но всё ещё корректный эквивалент; расширение
допуска само по себе проблему репро-строки не решает.

`find_cross_analogs` для СНП: ключи сравнения — `(d1,d2)` при конфигурации
NONE (тот же guard полноты, что итерация 19 ввела для буквы «А»: в этом
прайсе конфигурация NONE НИКОГДА не имеет d1 — 2 ключей `d2/d3`
недостаточно, чтобы отличить совпадение от разных типоразмеров, поэтому
NONE требует d1, которого нет ни у кого, и кросс для NONE всегда 0, как
раньше для буквы «А»); `(d2,d3)` [+`d4`, если есть в ОБЕИХ строках] — при
INNER/OUTER/BOTH, тот же принцип guard'а полноты, применённый по
конфигурации, а не по букве.

**Диагностика аналогов (`matching.diagnose_analogs`).** Чисто
информационная функция — не меняет `find_cross_analogs`/
`find_brand_analogs`, вызывается только когда обе таблицы аналогов для
выделенной строки пусты. Кросс-часть: топ-3 ближайших кандидата ДРУГОГО
стандарта по `|Δd2|+|Δd3|` — специально ШИРЕ, чем реальный фильтр
`find_cross_analogs` (любая буква/конфигурация, не только совпадающая),
сгруппированных по (Стандарт, Тип, DN_num) — одна строка на группу с
числом строк-толщин в скобках (`×2 толщины`), DN печатается целым числом
(`DN450`, не `DN450.0`). Брендовая часть: непустая только для категории
«Набивки» (`«брендовые аналоги только для категории «Набивки»»` —
единственная причина для остальных категорий). Диагностика по каждой
подсистеме считается только если сама подсистема реально дала 0 — иначе
строка была бы непустой даже при наличии настоящих аналогов:
`diagnose_analogs` отвечает строго на «почему аналогов нет», а не «что ещё
рядом». GUI (`gui.OrderTab.on_resolve`): при пустой таблице аналогов для
выделения статус-строка показывает первую строку `diagnose_analogs`
вместо молчаливого «Аналогов: 0» (кнопка не добавлялась — по заданию
задачи).

**Диагностика зеркалирует guard'ы кросса (хотфикс итерации 24).** Дефект
итерации 23: для типа А (конфигурация NONE) диагностика печатала фолбэк
«нет причины — должен был найтись» и перечисляла фантомов итерации 19
(ОСТ А/Б DN43, Δd2=1.0/Δd3=1.0) как «упущенные» аналоги, хотя их реально
отклоняет guard полноты ключей `find_cross_analogs` (у конфигурации NONE в
прайсе никогда нет d1 → кросс для NONE отключён целиком, §8/A13) — сам
guard в тексте диагностики не упоминался, а per-кандидатные причины
(конфигурация/допуск/материал) у этих фантомов совпадали с базой, поэтому
реальная причина отказа оставалась неозвученной.

Для каждого кандидата причина отклонения теперь строится **в порядке
проверки find_cross_analogs**: (а) полнота ключей размерности базы — guard
ГЛОБАЛЬНЫЙ (find_cross_analogs проверяет его ДО перебора кандидатов и, не
пройдя, отбрасывает разом ВСЕХ кандидатов, какими бы близкими они ни
были); (б) конфигурация колец (`core.TYPE_CONFIG`); (в) допуск
(`core.CROSS_TOL`); (г) материал. Поскольку guard (а) действует на ВСЮ
строку разом, в тексте он подставляется каждому кандидату, у которого
НЕТ иной содержательной причины (б/в/г) — если у кандидата уже есть
несовпадение конфигурации или допуска, эта причина информативнее и
остаётся единственной (пример: ОСТ-Б-DN477 → ASME Г/Д DN450, причина
`конфигурация OUTER ≠ NONE, допуск >1.0 мм` — guard не упоминается, так
как конфигурация уже объясняет отказ содержательно); если содержательной
причины нет (кандидат совпадает по конфигурации/допуску/материалу — как
ОСТ А/Б DN43 против типа А DN25), единственная настоящая причина —
guard (а): `недостаточная размерность: у типа А нет d1, кросс-стандарт
отключён (§8/A13)`. Если после всех четырёх проверок причина всё равно не
находится — это баг (рассинхрон диагностики и реального фильтра), текст
`«причина не определена: рассинхрон диагностики и фильтров»` служит
маркером такого расхождения и в норме не должен встречаться (gui_tests
тест 50 — прогон по ≥200 строкам каталога с пустым кроссом, включая типы
А/Б, подтверждает отсутствие маркера).

Тест 50 на первом прогоне нашёл ровно такое расхождение: ОСТ-Д-DN179 ↔
ГОСТ-Д-DN150 совпадали по конфигурации (BOTH) и по допуску d2/d3, но
`find_cross_analogs` их всё равно отклонял — причина оказалась в `d4`
(наружное кольцо), который `find_cross_analogs` добавляет в `eff_keys`,
когда он есть в ОБЕИХ строках (`use_d4`), а диагностика Δd4 вовсе не
считала. Допуск (в) исправлен: `Δd4` теперь тоже входит в проверку
превышения `core.CROSS_TOL`, когда `d4` есть и у базы, и у кандидата
(печатается в тексте как `Δd4=…`, только когда применимо).

**Перформанс-контракт диагностик (итерация 25).** `find_cross_analogs` и
`_diagnose_cross_analogs` раньше парсили `Основные_размеры` через
`core.norm_dims` построчно на КАЖДЫЙ вызов — на живом каталоге (8008 строк
категории «СНП») это O(кандидатов) регэксп-разборов за вызов, а тест 50
(`diagnose_analogs` на ≥200 базовых строках) и GUI-статус аналогов при
выделении строки без кросса складывали это в O(N_база × N_кандидатов)
разборов ОДНОГО И ТОГО ЖЕ df. `matching._dims_frame(df)` разбирает
`Основные_размеры` всего df ОДИН раз в числовые колонки `_d1.._d4` (NaN,
если ключа нет у строки) и кэширует результат по `(id(df), len(df))` — df
каталога в приложении неизменяем в рамках сессии (новый `build`/`build
--db` создаёт новый df, старый вытесняется из единственного слота кэша);
`len()` в ключе — дешёвая защита от коллизии `id()` после сборки мусора
предыдущего df. `find_cross_analogs` и `_diagnose_cross_analogs` больше не
вызывают `core.norm_dims` на кандидатов — маски допуска/дельты `Δd2/Δd3/Δd4`
считаются векторно по колонкам `_dims_frame` (pandas), группировка топ-3 в
диагностике — через `groupby(...).idxmin()`/`.nunique()` вместо
Python-словаря, собираемого в цикле по `cand.iterrows()`. Семантика и
тексты причин НЕ изменились (guard→конфигурация→допуск→материал, группировка
по (Стандарт,Тип,DN_num), маркер `«рассинхрон»`) — gui_tests тесты 36–50
сверены на идентичный вывод до/после векторизации. Бюджеты (тест 51,
`time.perf_counter`, живой каталог, кэш уже прогрет тестом 50): одиночный
`diagnose_analogs` < 1.0 с, одиночный `find_cross_analogs` < 0.5 с; полный
прогон `gui_tests.py` укладывается в 90 с.

## 12. Стыки исполнений и взаимозаменяемость типов, итерация 26

**Бизнес-правило (дано задачей, подтверждено разведкой каталога).**
Клиенты иногда описывают исполнение уплотняющей поверхности СНП не числовым
кодом каталога («2-3», «4-5», «8-9», «1-1» — `core.EXECUTIONS_GOST`,
`GOST_52376_RULES`), а буквенной парой лица фланца:

| Буквенный стык | Числовое исполнение | Типы (семья) |
|---|---|---|
| B-B (кириллица «В-В» / латиница «B-B»), «выступ/выступ» | `1-1` | Г, Д |
| E-F, «выступ-впадина» | `2-3` | А, В |
| C-D, «шип-паз» | `4-5`, `8-9` | А |

Таблица — прямое отражение уже существовавших `core.EXECUTIONS_GOST`
(`{"А": ["2-3","4-5","8-9"], "В": ["2-3"], "Г": ["1-1"], "Д": ["1-1"]}`) и
`GOST_52376_RULES`: буквенный стык — это просто другое имя того же
числового исполнения, поэтому таблица не вводит новых допущений о
взаимозаменяемости — она транслирует то, что уже было закодировано числами.
Разведка `groupby(('Стандарт','Тип_изделия'))['Исполнение']` по живому
каталогу (категория «СНП», 15 065 строк) подтвердила: колонка
«Исполнение» заполнена **только у ГОСТ** — у ОСТ/ASME её нет вовсе (пусто
для всех 13 буквенно-стандартных комбинаций из этих двух стандартов), и у
ГОСТ значения в точности совпадают с `EXECUTIONS_GOST`. Отсюда:
`core.JOINT_EXEC_PAIRS`/joint-фильтр в `resolve_customer` осмыслены только
для ГОСТ-заявок — это следствие состава прайса (у ОСТ/ASME просто нет
такой колонки), а не отдельная ветка «если стандарт ГОСТ» в коде.

**Разведка: семантика хвоста «10-40».** Репро-промах: «Прокладка
СНП-Г-В-В-10-40 ГОСТ Р 52376-2005 22шт» → 0 точных («не распознаны»).
Гипотезы для «10-40»: (а) DN=10 + PN=40 (обе точки), (б) DN=10 + диапазон
давления 10–40 без отдельной точки PN. Прямая проверка каталога (тип Г,
ГОСТ, исполнение «1-1», DN=10) даёт РОВНО 2 варианта давления:

| DN | PN / Давление | Давление_кгс_мин | Давление_кгс_макс |
|---|---|---|---|
| 10 | `1.0 - 6.3` | 1.0 | 6.3 |
| 10 | `10.0 - 40.0` | 10.0 | 40.0 |

Оба ключевых числа хвоста (10 и 40) буквально совпадают с границами ВТОРОЙ
строки — но так происходит для ЛЮБОГО DN этого исполнения (10, 15, 20, 25,
32, 40, 50, 65, 80 — везде диапазон `10.0 - 40.0` для «верхней» ценовой
полосы, DN≥175 сворачивается в одиночное значение `40`), поэтому «10-40»
не может быть ТОЛЬКО диапазоном давления без DN — иначе он был бы
неоднозначен между 9 разными DN. Выбрана семантика (а): **первое число —
DN, второе — точка PN**, встраиваемая в обычный `cust["pn"]`/`pressure_mask`
(проверка «точка входит в диапазон строки»), НЕ в `pn_lo`/`pn_hi`. У DN=10
диапазон `1.0-6.3` не содержит 40, диапазон `10.0-40.0` содержит — фильтр
однозначно выбирает вторую строку тем же механизмом, что уже обрабатывает
явный `PN 40` в любой другой заявке; отдельная «range-семантика» хвоста не
понадобилась. Тип Д при DN=10 в прайсе отсутствует вовсе (физически
начинается с DN=65 — см. ниже), поэтому для теста 54 взят DN=100, где оба
типа Г/Д существуют с одинаковыми d2/d3/d4 и диапазоном давления `1.0-6.3`.

**Разбор (`matching.JOINT_MARK_RE`, `parse_customer_line`).** Новый
регэксп — «СНП[-\s]?(тип)[-\s](В-В|B-B|E-F|C-D)[-\s](DN)[[-\s](PN)]» —
пробуется ДО обычного `MARK_RE` (та же исходная строка при буквах стыка на
месте цифр `MARK_RE` не матчит вовсе — исполнение там ожидает `\d+` сразу
после буквы типа). Литеральная альтернация (а не общий класс
`[A-Za-zА-Яа-я]`) — намеренно: репро «не-стыка» СНП-А-Е-Г-15-40» (буква
«Е», затем буква «Г» — НЕ входит ни в одну из трёх пар) обязана остаться
нераспознанной, как и раньше (регрессия — audit_lines-тест итерации 17,
классифицирует эту строку `unrecognized`); при общем классе букв регэксп
проглотил бы «Е-Г» как синтаксически валидный «стык», и код после матча
должен был бы ОТДЕЛЬНО отбраковывать бессмысленную пару — литеральная
альтернация проще и по построению не даёт такой строке вообще стать
`type`-распознанной. При успехе `JOINT_MARK_RE` НЕ трогает `cust["mark"]`
(остаётся `None`): каталожная маркировка этих позиций — числовая
(`"СНП-Г-1-1-10-(Ру)"`), не буквенный стык клиента; префиксное сравнение с
ней ничего не нашло бы, подбор целиком идёт через `type`+`joint`+`dn`+`pn`
(тот же паттерн, что ANSI-заявки с `dims_req` уже используют вместо mark).
Явные `DN N`/`PN N` (`explicit_dn`, `cust["pn"]` до этого шага) — по
прежнему в приоритете, как и у обычного `MARK_RE`.

**Resolve (`matching.resolve_customer`, `diagnose_miss`).** Новый шаг
`joint` — фильтр `df["Исполнение"].isin(core.JOINT_EXEC_PAIRS[cust["joint"]]
-в-виде-строк "N-M")`, применяется СРАЗУ после `type` (тип клиента
по-прежнему обязан совпасть точно — joint сужает ДОПОЛНИТЕЛЬНО, не вместо
типа). Fullmetal-развилка (бывший A8, итерация 17) была жёстко завязана на
`if cust.get("mark"):` — у joint-строк `mark` пуст, поэтому добавлена
СИММЕТРИЧНАЯ `elif cust.get("type") and len(res):` ветка. Ветка недостижима
для СТАРОГО пути `MARK_RE` (там `type` и `mark` всегда выставляются ВМЕСТЕ,
в одном `if m:`-блоке) — нулевой риск регрессии существующих тестов на
mark-based заявках.

*Устарело с итерации 27 (см. §7): сама fullmetal-развилка A8 отменена — обе
ветки `resolve_customer` больше не скрывают вторую ценовую группу по
умолчанию (это оказались два разных продукта, не дубль), поэтому
репро-строка теперь даёт 8 строк, а не 4. Симметричная `elif`-ветка для
joint-заявок осталась (нужна для правила «явное „как навитая" в заявке
сужает до fullmetal»), изменилось только то, что она сужает по умолчанию.*

**Аналоги: релаксация типа внутри семьи стыка.** Три новых места:

1. `matching.find_joint_analogs(df, row)` — для ВЫДЕЛЕННОЙ точной строки
   (кнопка «Аналоги» в GUI): joint базовой строки определяется ОБРАТНО, по
   её колонке «Исполнение» (`core.EXEC_TO_JOINT`), а не по `cust` — работает
   и для строк, найденных не через joint-заявку. Кандидаты — ТОТ ЖЕ
   Стандарт (это ключевое отличие от «кросс-стандарта»), Тип_изделия ∈
   `core.JOINT_TYPE_FAMILY[joint] \ {свой тип}`, тот же Материал, то же
   давление (Давление_кгс_мин/макс совпадают с базовой строкой — разведка
   DN=100 подтвердила: у пары Г/Д одного DN диапазон идентичен), размеры
   d2/d3[/d4] в допуске `core.CROSS_TOL` (тот же guard, что
   `find_cross_analogs`). «Причина»: `совместимый тип исполнения (стык
   B-B)` (код подставляется реальный, не список всех трёх).
2. `matching.find_smart_analogs` (каскад по `cust` из текста заявки) — если
   точный подбор (без стали/толщины) пуст И `cust["joint"]` задан, пробуется
   ТОТ ЖЕ std, но `type` заменён на `isin(семья)` — ДО падения `std`
   (релаксация типа внутри одного стандарта консервативнее смены стандарта
   целиком); `Причина` строки помечается так же, как в п.1.
3. **`find_cross_analogs` (кросс-СТАНДАРТ) НЕ тронут.** Задача просила
   расширить и «кросс-стандарте», но семейство стыка НЕ подразумевает
   совместимость МЕЖДУ стандартами — у СНП Г/Д (BB) кросс-стандартное
   сравнение уже идёт по `core.TYPE_CONFIG` (итерация 23) и корректно
   различает конфигурации OUTER/Г и BOTH/Д КАК РАЗНЫЕ между стандартами;
   ослаблять `find_cross_analogs` парой «любой тип из семьи стыка,
   независимо от `TYPE_CONFIG`» означало бы повторить именно тот риск
   фантомных совпадений, который итерации 19/23 специально устраняли
   (guard полноты ключей d1/d2 против случайного совпадения d2/d3 у разных
   типоразмеров) — без отдельной разведки допуска МЕЖДУ каждой парой
   стандартов эта расширение осталось бы недоказанным. Решение: держать
   «тот же стандарт, семья стыка» (`find_joint_analogs`, безопасно —
   работает в пределах одного прайс-листа, где допуски уже проверены §11)
   ОТДЕЛЬНО от «другой стандарт, конфигурация» (`find_cross_analogs`,
   не менялся) — честная граница вместо непроверенного расширения,
   в духе `CROSS_TOL_XSTD`, не введённого в §11 по той же причине.

**Guard аналогов на пустом cust.** `gui.OrderTab.on_analogs` (ветка
каскада по последней строке заявки, без выделения) проверяла только
`cust.get("mark") or cust.get("type") or "СНП" in line.upper()` — для
репро «СНП-А-Е-Г-15-40» это истинно (буквальное «СНП» в тексте), хотя
`parse_customer_line` не извлекла НИ ОДНОГО признака (`type`/`mark` оба
`None` — буквы «Е-Г» не входят ни в один стык, см. разбор выше). Без
дополнительной проверки `find_smart_analogs(df, cust)` с таким `cust`
резолвился бы БЕЗ единого фильтра — молчаливый «весь каталог как аналоги».
Новый guard: `if not matching.has_criteria(cust): статус «параметры не
распознаны — аналоги недоступны», return` — та же функция, что уже
защищает `resolve_customer`/`entry.cmd_order` (R1) в других местах, здесь
подключена в третье место.

**Регрессия проверена явно.** «СНП-В-2-3-250-16 ГОСТ» (числовое исполнение
в МАРКИРОВКЕ, не буквенный стык) по-прежнему идёт через старый `MARK_RE`
(joint остаётся `None`, joint-фильтр в `resolve_customer` не применяется
вовсе) → 4 строки, без изменений (gui_tests тест 5, CLAUDE.md регрессия).

## 13. Двухуровневые кросс-аналоги: «посадка» и «номинал», итерация 28

**Бизнес-требование.** При запросе по ГОСТ менеджер должен видеть позиции
ОСТ/ASME того же номинала (и обратно), даже когда точного размерного
совпадения нет — `find_cross_analogs` (единственный уровень до итерации 28)
даёт 0 для многих таких пар, хотя позиции того же DN в другом стандарте в
каталоге есть, просто их физический размер отличается больше допуска.
Решение — второй, явно более слабый уровень, а не расширение допуска
`CROSS_TOL` (расширять его означало бы тихо считать разные физические
размеры взаимозаменяемыми без предупреждения менеджеру).

**Tier 1 («посадка», не менялся).** `matching.find_cross_analogs` — та же
категория/конфигурация (СНП — `core.TYPE_CONFIG`, иначе — `core.cross_keys`
+ буква типа) и материал, ДРУГОЙ стандарт, размеры (d2/d3[/d4] у СНП) В
ДОПУСКЕ `core.CROSS_TOL`. DN_num кандидата и базовой строки в общем случае
РАЗНЫЙ (ГОСТ и ОСТ/ASME нумеруют DN по-разному — итерации 19/23) —
совпадение DN_num не требуется и не проверяется.

**Tier 2 («номинал», новый).** `matching.find_cross_nominal_analogs` — те
же категория/конфигурация/материал, ДРУГОЙ стандарт, ТОТ ЖЕ DN_num, но
размеры НЕ все в допуске `CROSS_TOL` (строки, уже отданные tier 1,
исключаются — не дублируются). Смысл: «эта позиция в другом стандарте
называется тем же номинальным диаметром, но её реальный размер может не
совпасть — проверьте посадку сами», а не утверждение взаимозаменяемости.
«Причина»: `номинал: тот же DN в <Стандарт>; Δd2=…, Δd3=… (Δd4=…) —
проверить посадку»; до 6 строк, сортировка по сумме дельт по возрастанию.

**Разведка (СНП/Овальные/Восьмиугольные, живой каталог 15493 строк).**
Пары (конфигурация, DN_num), где есть строки ≥2 стандартов, с дельтами
Δd2/Δd3 (мм) между БЛИЖАЙШИМИ по размеру строками пары:

| Стандарты | Конфиг | DN | Тип | Δd2 | Δd3 | Tier |
|---|---|---:|---|---:|---:|---|
| ASME↔ГОСТ | OUTER | 80 | Г | 1.6 | 0.7 | 2 |
| ASME↔ГОСТ | BOTH | 80 | Д | 1.6 | 0.7 | 2 |
| ASME↔ГОСТ | OUTER | 20 | Г | 0.4 | 1.4 | 2 |
| ASME↔ГОСТ | OUTER | 32 | Г | 0.8 | 2.5 | 2 |
| ASME↔ГОСТ | BOTH | 125 | Д | 1.4 | 4.8 | 2 |
| ASME↔ГОСТ | BOTH | 250 | Д | 2.3 | 8.5 | 2 |
| ASME↔ГОСТ | OUTER | 300 | Г | 0.1 | 10.7 | 2 |
| ASME↔ГОСТ | BOTH | 600 | Д | 2.3 | 20.5 | 2 |
| ГОСТ↔ОСТ | INNER | 250↔292 | В | — | — | 1 (разный DN_num, посадка совпала) |

Итого 32 пары tier 2 у СНП (все ASME↔ГОСТ, конфигурации OUTER/Г и BOTH/Д);
0 у типа А (config NONE — гвард отсутствия d1, тот же, что у tier 1, §8/
A13); 0 у ОСТ — ОСТ не делит DN_num ни с ГОСТ, ни с ASME для Г/Д в этом
каталоге; 0 у «Овальные»/«Восьмиугольные» — `core.cross_keys("Овальные")`
требует ключ `"D"`, которого нет ни у одной строки категории (реальные
ключи `Основные_размеры` — OD/ID/P/A/В), `core.cross_keys("Восьмиугольные")`
возвращает `[]` (не покрыта справочником вовсе) — гвард `any(k not in base
for k in keys)` отключает tier 1 И tier 2 для обеих категорий одинаково;
это существующее ограничение `core.cross_keys`, не новый баг и не в
периметре задачи (`core.py` не менялся).

**Правило.** Номинал НЕ утверждает совместимость посадки — только то, что
позиция в другом стандарте называется тем же диаметром DN. Решение о
замене — за менеджером, отсюда явная пометка «проверить посадку» в каждой
причине tier 2 и отдельный визуальный тег в GUI (`COLOR_NOMINAL`, отличный
от `COLOR_CROSS`).

**GUI.** `gui.OrderTab.on_analogs` (ветка выделенной строки) объединяет
`find_joint_analogs` → `find_cross_analogs` (tier 1) → `find_cross_nominal_
analogs` (tier 2) → `find_brand_analogs`; tier 1 в таблице аналогов идёт
раньше tier 2 (порядок вставки в `analog_tree`, сортировку/агрегаты не
меняет). Статус-строка: `аналогов: N (посадка: X, номинал: Y)`, где `N` —
сумма всех четырёх подсистем (joint+tier1+tier2+brand), `X`/`Y` — отдельно
tier 1/tier 2. При `N == 0` (пусты все четыре, включая оба кросс-уровня) —
прежний вызов `matching.diagnose_analogs` (не менялся) добавляет первую
строку диагностики к статусу, как и до итерации 28.

**Перформанс.** `find_cross_nominal_analogs` использует тот же кэш
`_dims_frame` (итерация 25), что `find_cross_analogs` — одиночный вызов
< 0.5с (бюджет §11, тест 51 не менялся; отдельный замер в тесте 57).

## 14. Бренд-эквиваленты набивок, NULL-цена, отказ от «OWN», итерация 31

**Классы эквивалентности — источник данных, не логика.** `matching.
find_brand_analogs`/`_brand_group_of` не менялись ни строкой (по заданию) —
поменялся только `core.load_brand_groups()`: с этой итерации список классов
`(brand, mark)` строится из `core.load_brand_equivalents()`
(`src/data/brand_equivalents.json` — 17 классов, таблицы 2+3
`vendor_tables_2026-09.md`, объединённые по колонке Vendor D, без
Vendor V/Vendor W, плюс VS/Vendor I), а не из старого
`brand_groups.json`/`core.BRAND_GROUPS` (та константа сохранена только ради
`entry.py::cmd_dump_data`). Формат вывода (список списков `(brand, mark)`)
не изменился, поэтому вся резолюция/сравнение брендов (`_brand_key`,
bidirectional `startswith`) работает как раньше — в том числе её известная
неточность (короткие коды могут перекрёстно совпасть с чужим классом,
напр. «С-101» класса 1 против «С-101С» класса 2) — это СУЩЕСТВУЮЩЕЕ
свойство функции, не новое и не исправлялось (см. `catalog._brand_present`
ниже — там для ДОЛИВКИ каталога понадобилась более строгая проверка именно
из-за такого рода ложных совпадений, но сама `find_brand_analogs` эту
проверку не использует и не обязана).

**`catalog._brand_present` — точнее, чем префиксное сравнение
`apply_manual_packings`.** Наивная substring-проверка нормализованной
маркировки («ключ есть где-то внутри блока») поймала в разведке ложное
совпадение: «Гермапрум С-610 16х16» после `core.norm_brand` склеивается в
блок, оканчивающийся на «...UMC610» (хвост «...М» слова «ГЕРМАПРУМ» +
код «C610» от «С-610» встык) — это СЛУЧАЙНО содержит подстроку «MC610»,
код СОВСЕМ ДРУГОГО бренда (Vendor A, тот же класс эквивалентности, но
другой код, физически другая маркировка). Правильная проверка — по ЦЕЛЫМ
словам маркировки: список нормализованных слов, ключ кандидата ищется как
точное совпадение (или префикс) СМЕЖНОЙ последовательности целых слов, а не
произвольного среза блока.

**NULL-цена («цена по запросу»).** `matching.sort_for_manager` уже был
безопасен для `NaN`-цены до этой итерации (`na_position="last"` на колонке
`_price` — см. §1 выше) — правок не понадобилось. `gui.OrderTab._add_to_kp`
(единственная точка, где NaN раньше тихо превращался в 0.0 и попадал в
КП бесплатной позицией) теперь блокирует добавление диалогом «Цена не
задана — позиция только для подбора аналога» ДО коэрсии.

**Отказ от «OWN (собств. производство)».** Маркер `core.SUPPLIER_OWN_MARK`
(`"OWN (собств."`) остался в коде ради обратной совместимости

## 18. Ближайшие варианты при промахе (итерация 41)

**Задача.** Заявка «Сальниковая набивка RK-240 I 5х5мм» давала «Точных позиций: 0»
и «кандидатов» АФТ/VS, совпавших только по слову «набивка» (`diagnose_search`).
Разведка: токен «I» короче 2 символов отбрасывается (A11), «сальниковая», «rk-240»,
«5x5мм» в каталоге не встречаются. В каталоге всего две RK-строки (RK-250 8х8,
RK-250-G 14х14, цена NULL, поставщик Vendor R).

**Функция.** `matching.nearest_variants(df, line, cust, limit=30)` -> колонки каталога
+ «Причина» + «Уровень». Вызывается ТОЛЬКО при пустом точном подборе и только вне
СНП-маршрута; у заявки с точными позициями не вызывается. Строки не дублируются между
уровнями, df и `resolve_customer`/`search_generic`/`search_with_criteria`/
`find_brand_analogs` не меняются.

| Уровень | Что | Причина (пример) |
|---|---|---|
| a | код заявки есть в справочнике `data/vendor_r_rk_2026-09.json` (`core.load_rk_catalog`): строки каталога, соответствующие аналогам кода (`analogs_table` ∪ `analogs_card`); сортировка: ближайшее сечение, порядок аналогов, наличие, цена | «аналог по данным поставщика (таблица vendor_r): RK-240I ≈ МС 131 (сайт противоречив)» |
| b | то же семейство: строки категории, у которых в маркировке целым словом стоит префикс семьи заявки; сортировка: |Δ числовой части кода|, |Δ сечения|, наличие, цена | «ближайший вариант: семейство RK, код RK-250 (запрошен RK-240I), сечение 8х8 (запрошено 5х5)» |
| c | (a) и (b) пусты: топ-3 по числу совпавших токенов (как `diagnose_search`) | «слабое совпадение: только общие слова» |

Если код есть в справочнике, а в каталоге его нет — первая строка ответа получает
префикс «RK-240I есть у Vendor R (ТРГ: …), в каталоге отсутствует».

**Склейка суффикса.** «RK-240 I» -> «RK-240I»: пробел + ОДНА латинская буква (без
пробела — до трёх букв) склеивается, только если склеенный код есть в справочнике или
в каталоге; иначе остаётся «RK-240». Справочные коды сравниваются без пробелов/дефисов
(«RK-250-G» = «RK-250G»).

**Guard семейного ключа.** Префикс — не короче 2 букв и СРАЗУ (через необязательный
пробел/дефис) цифра: `RK-240`, `МС101` — да; голые «Н»/«С» — нет. Разведка (Набивки/
Ленты): «Н» 15+9 (латинская H), «С» 27 строк — как подстрока они ловят «МС», а ключ с
границей слова — нет (прецедент итерации 29: «АФ»/«НА» ловили «гРАФит»/«НАбивка»).
Сравнение — по свёрнутому виду (`core._CYR2LAT_BRAND`: МС=MC, Н=H, С=C): в каталоге
код бренда встречается в обоих алфавитах, `_norm_mark_series` омоглифы не сворачивает.
Ключи аналогов справочника точные (код целиком «префикс+число», префикс от 1 буквы) —
поэтому «Н 1300» находит «Н-1300»/«XTex H 1300», но не «Н-13000».

**Почему это аналог, а не точная позиция.** RK-240I (ТРГ + Inconel) и МС131 — разные
изделия разных производителей; соответствие даёт таблица поставщика, а не каталожный
код. Поэтому ближайшие варианты: отдельный тег/цвет в GUI, «Причина» видна, в КП идут
как аналоги («ближайший вариант — требует подтверждения»), вне суммы `order`.

**Конфликты источника.** 6 кодов справочника, где таблица аналогов и карточки сайта
расходятся (RK-240I, RK-240SS, RK-240CC, RK-270HG, RK-250G, RK-250GSC-«не дочитан»):
поле `note`; причина строки уровня (a) получает «(сайт противоречив)».

**GUI/CLI.** OrderTab: родитель «✗ нет точного совпадения — ближайшие варианты: N»
(развёрнут), дети — тег `nearest`, колонка «Причина»; в отпечаток дублей групп (§9) не
входят. `entry.py search`: «Нет точного совпадения» + блок ≤15 строк с причинами;
`order`: в блок аналогов вне суммы; `audit_lines`: промах остаётся промахом (hit-rate
не меняется), `summary["misses_with_nearest"]`.

### Примечание (итерация 42): регулярные и нерегулярные товары

## 19. Исправления по ручной проверке 30.09.2026 (итерация 50)

- **Давление колец.** `matching.row_pressure_kgs(row) -> (lo, hi, rated)` — единый источник для `pressure_hit`/`pressure_range_hit`/`_miss_hint`: числовые «Давление_кгс_*», иначе у `core.PRESSURE_TEXT_MPA_CATEGORIES` («Овальные», «Восьмиугольные») — текст «PN / Давление» в МПа через `core.pressure_range` (×10). `rated=True` и давления нет (ASME-кольца) → при заданном PN строка НЕ проходит. Асимметрия (намеренная): СНП ASME и категории без давления (набивки, прокладки…) — `rated=False`, «проходят всегда», как раньше. Выбор «фильтр читает текст», а не «заполнять кгс при сборке»: каталог/БД не меняются, а `Давление_кгс_*` входят в постоянный ключ физической позиции для интеграции со складской системой — заполнение сменило бы ключи всех кольцевых позиций.
- **Количество не токен.** `matching.split_qty`/`normalize_request_line` — первая операция `parse_customer_line`, `search_generic`, `_remaining_tokens`, `diagnose_search`, `nearest_variants`/`_nv_weak` (и через них `audit_lines`). Число обязано стоять отдельно (`(?<![\w.,])`), «x N» — количество, только если слева не голое число. Набивка: «10мм» без NxN → «10х10» (иначе толщина → маршрут критериев → 0 строк).
- **Свёртка кода (A15).** `_code_fold` (UPPER, Х→X, омоглифы `core._CYR2LAT_BRAND`, без пробела/дефиса между буквой и цифрой и без дефиса между буквами) — ДОПОЛНИТЕЛЬНОЕ условие `_token_hit` к прежнему подстрочному (выдача только расширяется), с левой границей кода. `_search_tokens` склеивает «буквы(1–4) + число» в код, только если свёртка есть в каталоге. Следствие: «Набивка МС 500 10х10» — 2 строки вместо 3 (третьей была «Гермапрум С-500» по случайному «мс» в «гермапруМ С»).
